# Marketplace for business

Управляемый маркетплейс услуг и товаров с полным сопровождением сделки
в B2B-сегменте.

**Клиент работает с площадкой как с маркетплейсом:** открывает каталог, сам
смотрит услуги и товары разных компаний, сравнивает и выбирает. Подбор —
не основной путь, а персональные предложения по интересам клиента.

**Конкурентное преимущество — сопровождение и гарант сделки, а не каталог.**
Каталог копируется за месяц; договор, счёт, акт, удержание денег до приёмки,
разбор рекламации и ответственность за результат — нет. Поэтому площадка
**не сводит стороны, а сама является стороной сделки**: ведёт сделку, выпускает
документы, принимает оплату, удерживает комиссию 6–15 % и отвечает за результат.

**Гарант работает удержанием:** деньги клиента лежат у площадки до подписания
акта. Подрядчик получает выплату после приёмки, при рекламации деньги не уходят
до разбора.

**Цель — объединить предпринимателей МСП.** Начинаем с плацдарма: микро- и малый
бизнес с физической точкой (кафе, салоны, клиники, магазины, небольшие офисы)
и пять категорий — санобработка, клининг, инженерка (ОВиК, электрика, сантехника),
охрана труда и СОУТ, профхимия и расходники.

**Кто пользуется системой:** заказчик — владелец точки, выбирает услугу в каталоге;
подрядчик — ИП или самозанятый, публикует карточки услуг с ценой и выполняет работу;
оператор — сотрудник площадки, модерирует карточки, разбирает очередь и гасит споры.

## Состояние

**Спринты 01 и 02 закрыты целиком, спринт 03 — в сокращённом объёме**
(решение от 15.09.2026). Сейчас в работе сделка: заказ из каталога,
путь до приёмки и документы готовы. Осталась настоящая оплата.

Что уже работает:

- **Регистрация и вход:** шторки «Войти» и «Регистрация», подтверждение почты
  кодом, вход по паролю, приглашение сотрудников, сессии и роли
- **Письма** с журналом доставки: в разработке пишутся в лог, отправка по SMTP
  включается настройкой
- **Очередь событий и процесс-разборщик:** изменение данных и запись события —
  одна операция, всё остальное уходит следом отдельным процессом
- **Каталог:** категории, подрядчики, зоны и карточки услуг, отбор кандидатов,
  экраны оператора и демо-данные (`pnpm db:seed`)
- **Витрина:** сетка карточек, фильтры по категории и зоне, поиск, карточка
  услуги с блоком «Как защищена сделка», четыре состояния
- **Саморегистрация подрядчика:** страница «Стать подрядчиком», проверка ИНН
  на опечатку по контрольной сумме, очередь ручной проверки у оператора.
  Справочник компаний ещё не выбран (Q20), поэтому пока туда попадает каждая
  заявка — регистрация от этого не страдает и отказов не бывает
- **Кабинет клиента:** точки (адреса, куда приезжает подрядчик), реквизиты
  компании и приглашение сотрудника письмом. Округ точки выбирается
  из списка — код, набранный руками, молча обнулил бы подбор
- **Журнал изменений:** кто, что и когда изменил, со старым значением
  и новым. Пишется в той же операции, что и само изменение, поэтому
  не врёт при откате; править его нельзя — таких команд нет в модуле
- **Второй путь клиента:** задача своими словами, когда в каталоге нет
  подходящей услуги. Номер, который можно назвать вслух; адрес из точки,
  снимком; очередь у оператора с текстом клиента целиком
- **Заказ из каталога и сделка:** клиент заказывает услугу, подрядчик видит
  заказ, обе стороны ведут его до приёмки. Закрыть сделку можно только через
  подписанный акт, при споре деньги замирают до решения оператора
- **Документы:** договор и счёт при подтверждении заказа, акт при готовности
  работы. Нумерация без пропусков и дублей — сорвавшийся выпуск номер
  возвращает. Выпущенный документ не меняется: только аннулирование
  и новый. Настоящей оплаты ещё нет
- Next.js 15 (App Router) + TypeScript strict + pnpm, `pnpm build` проходит
- Дизайн-токены обеих тем и примитивы `src/ui/` по утверждённым макетам `design/`,
  шрифт Manrope лежит в репозитории и не тянется с зарубежных серверов
- Пороги контраста §7.6, разведение ролей цвета §7.2 и типографическая шкала §7.3
  проверяются тестами: правило дизайна — проверка, а не пожелание
- Конфиг через Zod: приложение падает на старте, если переменной не хватает
- Drizzle + drizzle-kit, первая миграция создаёт схему `platform`
- Структурный лог pino, каркас процесса-воркера с корректной остановкой
- Правило ESLint, запрещающее импорт глубже `modules/<name>/index.ts`, с тестами
- systemd-юниты, скрипт деплоя, ежедневный дамп и проверка восстановления
- Запуск на своей машине под Windows через Open Server Panel:
  `docs/13-local-server.md`

**Демо** собирается автоматически при каждом изменении интерфейса и выкладывается
на GitHub Pages — временная замена серверу, пока его нет. Настройка:
`.github/workflows/demo.yml`; перед первым запуском включить Pages в настройках
репозитория (Settings → Pages → Source: GitHub Actions).

Не закрыто: деплой на сервер и проверка восстановления из дампа на живой базе —
нет доступов (Q7 в `docs/06-open-questions.md`).

## Архитектура коротко

Модульный монолит: одно приложение Next.js, один процесс воркера, один сервис
`ai-service` на Python, одна база PostgreSQL. Три процесса на одном VPS в России.

Девять модулей, у каждого своя схема в базе, свой публичный интерфейс и свои
события. JOIN между схемами запрещены, побочные эффекты идут через таблицу
`platform.outbox` и разбираются воркером. Границы нарезаны так, чтобы переход
к сервисам был выделением, а не переписыванием — порядок и стоимость выделения
в `CLAUDE.md` §2.

```
src/modules/  platform · catalog · intake · matching · deal
              documents · payments · notifications · analytics
src/app/      роуты Next.js, тонкие: только вызов модулей
src/worker/   процесс разбора outbox
src/ui/       дизайн-система: токены, примитивы, паттерны
src/shared/   типы, утилиты, конфиг — без бизнес-логики
```

## Стек

Next.js 15 (App Router) · TypeScript strict · pnpm · PostgreSQL 16 ·
Drizzle ORM · Zod на каждой границе · Tailwind + shadcn/ui · grammY ·
pino · Vitest · Python + FastAPI для `ai-service`.

## Разработка

Нужны Node 22+, pnpm и PostgreSQL 16.

```bash
cp .env.example .env     # заполнить; приложение падает на старте, если чего-то нет
pnpm install
pnpm db:migrate
pnpm db:seed             # демо-данные, только для разработки
pnpm dev                 # приложение на localhost:3000
pnpm worker              # процесс разбора outbox
```

Проверки, которые должны проходить перед тем, как считать задачу готовой:

```bash
pnpm typecheck && pnpm lint && pnpm test
```

`.env` в репозиторий не попадает. Скрипты на `tsx` читают его флагом
`--env-file-if-exists`; в проде переменные приходят из systemd (`deploy/README.md`).

## Что обязательно и не обсуждается

- **Персональные данные россиян — только на серверах в РФ** (152-ФЗ). Касается базы,
  сервиса ошибок, аналитики и почтового шлюза. Зарубежные SaaS не подходят.
- **Вебхуки эквайринга идемпотентны.** Двойное начисление комиссии на одну оплату —
  самая дорогая из возможных ошибок.
- **Нумерация счетов и актов — без пропусков и дублей**, последовательность в базе.
- **Статусы `disputed` и `cancelled` делаются вместе с остальными.** Обработка
  рекламаций — та самая гарантия, за которую берётся комиссия.
- **Тесты обязательны** для денежных расчётов, переходов статусов сделки и прав доступа.

Развёрнуто — в `CLAUDE.md` §8.
