# Ставки комиссии: не число, а правила

Решение от 27.08.2026: ставка комиссии перестаёт быть настройкой сервера
и становится подсистемой правил. Требуется три уровня.

**Два вопроса про смысл этих правил открыты — Q15 в `docs/06-open-questions.md`.**
Пока на них нет ответа, проектируется только каркас: структура правил, их история
и фиксация применённой ставки. Условия выбора — после ответов.

---

## Три уровня, от общего к частному

| Уровень | Пример | Кто задаёт |
|---|---|---|
| **Стандартная по категории** | санобработка 13 %, профхимия 7 % | администратор |
| **Акционная** | скидка за электронный документооборот | администратор |
| **Индивидуальная** | оборот свыше 1 млн → 1 % | правило, считается автоматически |

Правило одно: **побеждает самая частная подходящая ставка.** Индивидуальная
сильнее акционной, акционная сильнее категорийной. Если на одном уровне
подошли две — побеждает та, что начала действовать позже.

## Две лестницы скидок и почему они не складываются

Индивидуальные условия считаются **и для подрядчика, и для клиента**, по разным
правилам: подрядчик получает скидку за объём выполненной через площадку работы,
клиент — за объём заказов.

Три решения, без которых эта пара не работает:

**Обе скидки уменьшают комиссию площадки, а не цену и не выплату подрядчику.**
Иначе скидку клиенту оплачивал бы подрядчик — за то, что клиент много заказывает
у кого-то другого. Подрядчики ушли бы быстрее, чем клиенты пришли.

**Скидки не складываются.** Берётся меньшая ставка из двух подошедших.
Сложение выглядит щедро, но при двух лестницах плюс акции комиссия уходит
в ноль за пару сделок.

**У комиссии есть нижняя граница.** Задаётся администратором, по умолчанию 1 %.
Без неё правила рано или поздно дадут отрицательную комиссию, и площадка начнёт
доплачивать за то, что сводит стороны. Граница проверяется в коде и покрыта
тестом — это тот случай, когда ошибка стоит прямых денег.

**Оборот считается за скользящий год**, а не за всё время: иначе скидка,
заработанная однажды, останется навсегда, даже если подрядчик перестал работать.
Период задаётся администратором.

## Главное требование: ставка фиксируется в сделке вместе с причиной

```
Сделка № 1240
  ставка:      1 %
  правило:     «Объём: свыше 1 млн»
  обоснование: «оборот подрядчика на 25.08.2026 — 1 240 000 ₽»
  зафиксировано: 25.08.2026 18:20
```

Причина обязательна, и это не бюрократия. Через полгода придётся отвечать
подрядчику, бухгалтеру или проверяющему, почему в этой сделке взяли 1 %,
а в соседней 13 %. Ответ «так посчиталось» не годится: пересчитать задним числом
нельзя, потому что пороги оборота к тому моменту уже другие.

Отсюда же следует: **изменение любого правила никогда не трогает существующие
сделки.** Сделка помнит свою ставку, а не смотрит в справочник.

## Как это ложится в данные

```sql
-- Правила живут в payments: комиссия — его зона ответственности
create table payments.commission_rules (
  id             uuid primary key,
  kind           text not null check (kind in ('category','promo','individual')),
  rate           numeric(5,4) not null check (rate > 0 and rate < 1),
  category_id    uuid,          -- для kind = 'category'
  subject_org_id uuid,          -- для kind = 'individual': чья это ставка
  subject_side   text check (subject_side in ('contractor','client')),
  conditions     jsonb not null default '{}',  -- пороги оборота, признаки акции
  priority       int not null default 100,
  effective_from timestamptz not null,
  effective_to   timestamptz,   -- null = бессрочно
  note           text not null, -- то, что увидит человек в обосновании
  created_by     uuid not null,
  created_at     timestamptz not null default now()
);
```

Ставка — `numeric`, а не `float`: 0.13 должно остаться 0.13, а не стать
0.13000000000000001. Сама комиссия по-прежнему считается в копейках целыми
числами и округляется вниз, в пользу подрядчика (`src/shared/money.ts`).

В сделке добавляются `commission_rate`, `commission_rule_id`,
`commission_reason` и `commission_fixed_at`.

## Что покрывается тестами обязательно

Это деньги, поэтому тесты не по желанию (§8 `CLAUDE.md`):

- Выбор правила при нескольких подходящих — приоритет соблюдён
- Изменение правила не меняет комиссию в уже созданной сделке
- Пересечение порогов оборота на границе: ровно 1 000 000 ₽ — какая ставка
- Комиссия плюс выплата всегда равны цене, при любой ставке
- Ставка вне диапазона (0 или 1 и больше) не сохраняется

## Цена

| Что | Часов |
|---|---|
| Структура правил, приоритет, история | 14 |
| Расчёт оборота и пороги для двух лестниц сразу | 16 |
| Фиксация применённой ставки с обоснованием в сделке | 4 |
| Управление правилами и акциями в админке | 14 |
| Тесты | 8 |
| **Итого** | **56** |

Против 10 часов на вариант «ставка с датой начала действия» и 0 часов
на «оставить в настройках сервера».

**Акционная ставка за электронный документооборот сюда не входит.** Чтобы дать
скидку за электронную подпись, надо сначала уметь подписывать электронно —
это отдельные ~56 часов и договор с оператором, см. Q16
в `docs/06-open-questions.md`.

## Когда это делается

Вместе с модулем `payments`, а не в админском спринте. Причина простая:
управлять ставками, пока по ним не проходят деньги, нечем — проверить
правильность правил можно только на настоящей сделке. Админские экраны
для ставок делаются в том же спринте, что и сам движок.
