## 01-1. Каркас и деплой — 10 ч

Создать проект, поднять базу, выкатить на сервер. Пустая страница в проде лучше,
чем красивое приложение на ноутбуке.

**Сделать:**

- Next.js 15 (App Router) + TypeScript strict + pnpm
- Tailwind + shadcn/ui. **Токены до компонентов:** нейтраль, акцент, статусы,
  типографическая шкала, отступы, радиусы — в конфиге Tailwind, обе темы сразу.
  Цветов и размеров «по месту» в компонентах быть не должно (см. раздел 7 `CLAUDE.md`)
- Папка `ui/`: примитивы (кнопка, поле, таблица, бейдж статуса) и четыре состояния
  списка — пустое, загрузка, ошибка, успех
- Базовый макет: шапка с поиском, горизонтальное меню под ней во всю ширину,
  контентная область без боковой колонки (см. макеты в `design/`). Меню называет
  разделы задачами пользователя, а не сущностями системы
- Drizzle + drizzle-kit, подключение к PostgreSQL, первая пустая миграция
- pino, структурный лог с уровнями, в проде — в файл, в разработке — в консоль
- Конфиг через Zod: приложение падает на старте с понятной ошибкой,
  если переменной окружения не хватает
- Правило ESLint, запрещающее импорт из `modules/*/…` глубже `index.ts`
- systemd-юниты для `app` и `worker`, скрипт деплоя (git pull, build, migrate, restart)
- Ежедневный дамп базы по cron с выгрузкой в S3

**Готово, когда:**

- `pnpm typecheck && pnpm lint && pnpm test` проходят на пустом проекте
- Приложение открывается по домену, отдаёт страницу с версией сборки
- `pnpm db:migrate` отрабатывает на сервере
- Дамп базы создался, **и восстановление из него проверено** на пустой базе
- Попытка импортировать `modules/platform/service` из другого модуля падает на линтере
- Макет не даёт горизонтальной прокрутки страницы при ширине окна 360 px —
  мобильная вёрстка следующим этапом, но ломаться уже сейчас не должна

## 01-2. platform: организации, пользователи, вход — 28 ч

Переработана 27.08.2026: добавлены пароль и самостоятельная регистрация.
Было 16 часов при входе только по ссылке.

**Сделать:**

- Таблицы `platform.orgs`, `users`, `credentials`, `login_tokens`,
  `sessions`, `login_attempts` по `docs/03-data-model.md`
- **Регистрация:** форма → письмо со ссылкой → экран установки пароля →
  учётная запись активна. Почта считается подтверждённой только после перехода
  по ссылке
- **Два способа входа, оба рабочие:** по паролю и по ссылке на почту.
  У одного человека могут быть оба сразу
- Пароль хранится медленным хэшем; ссылка — быстрым отпечатком.
  Ни то, ни другое не хранится в открытом виде
- **Ограничение частоты по журналу попыток:** не больше трёх писем на адрес
  за 15 минут; после пяти неверных паролей подряд вход по паролю для этого
  адреса приостанавливается с нарастающей задержкой
- Восстановление пароля: та же ссылка на почту, назначение `reset_password`
- Сессия живёт 30 дней, продлевается не чаще раза в сутки, при выходе
  удаляется из базы
- Роли: `owner`, `staff`, `operator`, `admin`. Хелпер `requireRole()`
  для серверных экшенов
- Публичный интерфейс модуля: `getOrg`, `getUser`, `createOrg`, `register`,
  `inviteUser`, `verifyEmail`, `setPassword`, `startLogin`, `completeLogin`,
  `loginWithPassword`, `getSession`, `logout`

**Готово, когда:**

- Человек регистрируется, получает письмо, ставит пароль и входит
- Он же входит второй раз паролем, а третий — по ссылке: оба способа работают
- Просроченная и повторно использованная ссылка дают понятную ошибку, а не 500
- Есть тест: пользователь с ролью `staff` не может вызвать команду,
  требующую `operator`
- Есть тест: чужая сессия не даёт доступа к данным другой организации
- Есть тест: после пяти неверных паролей шестая попытка отклоняется
- Есть тест: в базе нет ни одного пароля и ни одной ссылки в открытом виде
- Есть тест: ответ на незнакомую почту не отличается от ответа на знакомую
- Письмо уходит через российский SMTP; в разработке пишется в лог

## 01-3. platform: outbox и воркер — 8 ч

Самая важная задача спринта: на этот механизм ляжет вся система.

**Сделать:**

- Таблица `platform.outbox`
- `publish(tx, event)` — записывает событие **в переданную транзакцию**, не в новую
- Реестр подписчиков: `on('deal.accepted', handler)`, регистрация при старте воркера
- Процесс `worker`: каждые 5 секунд берёт до 50 необработанных событий
  под `pg_advisory_xact_lock`, вызывает подписчиков, ставит `processed_at`
- При ошибке: `attempts + 1`, повтор с задержкой 5с → 30с → 5м → 30м,
  после 10 попыток запись `last_error` и остановка по этому событию
- Метрика: сколько событий не обработано и возраст самого старого

**Готово, когда:**

- Есть тест: событие, опубликованное в транзакции, которая откатилась, не появилось в outbox
- Есть тест: подписчик, вызванный дважды на одно событие, не создаёт двойного эффекта
- Есть тест: падающий подписчик не блокирует обработку остальных событий
- Воркер переживает перезапуск: события, взятые в работу и не законченные, обрабатываются снова
- В логе видно `eventId`, `type` и время обработки каждого события

**Сделать:**

- Сид: 12 категорий первой волны (санобработка, дезинсекция, дератизация, клининг,
  ОВиК, электрика, сантехника, охрана труда, СОУТ, пожарная безопасность,

- Публичный интерфейс: `getContractor`, `listContractors`, `findCandidates`,
  `getCategory`, `listCategories`, `listZones`
- `findCandidates({ categoryId, zoneCode, limit })` — правила отбора: активный статус,
  совпадение категории, покрытие зоны, сортировка по ручному рейтингу.
  **Это будущий запасной путь для ai-service — писать сразу как настоящую функцию**
- `listZones()` — единственный источник кодов зон. Заявка и карточка берут коды
  отсюда, руками их не вводит никто (см. «Мелкие замечания» в `docs/06-open-questions.md`)

**Готово, когда:**

- Оператор заводит подрядчика с категориями и зонами за один экран
- `findCandidates` возвращает корректный список на демо-данных, покрыт тестом
- Заведение подрядчика с `org_id`, которого нет в `platform.orgs`, отклоняется
  с понятной ошибкой — граница модулей проверяется кодом, а не базой
- Нигде в коде `catalog` нет запроса к таблицам схемы `platform`

**Урезано против исходного плана на 4 ч:** экраны оператора делаются в минимуме,
потому что в спринте 02 подрядчик начнёт заводиться сам (решение Q10) и часть
этих экранов всё равно переписывается.

## 01-5. catalog: карточки услуг — 12 ч

Каталог — основной путь клиента, и начинается он здесь. Публичной витрины
в этом спринте ещё нет: сначала должно быть что показывать.

**Сделать:**

- Таблицы `catalog.listings`, `catalog.listing_zones` по `docs/03-data-model.md`
- Кабинет подрядчика: список своих карточек, создание, редактирование, снятие.
  Статусы `draft` → `pending` → `published` / `rejected` → `archived`
- Экран оператора «Очередь модерации»: карточки в `pending`, публикация
  и отклонение с `rejection_note`
- Публикация карточки → событие `listing.published` в outbox в одной транзакции.
  Отклонение → `listing.rejected`
- Публичный интерфейс: `createListing`, `updateListing`, `submitListing`,
  `publishListing`, `rejectListing`, `archiveListing`, `getListing`, `listListings`
- Проверка при публикации: зоны карточки входят в зоны подрядчика,
  `price_kopecks > 0`, категория активна

**Готово, когда:**

- Подрядчик создаёт карточку, отправляет на модерацию, видит причину отклонения
  и может исправить
- Оператор публикует карточку, в `platform.outbox` появляется `listing.published`,
  воркер его обработал
- Есть тест: переход `draft → published` минуя `pending` запрещён
- Есть тест: подрядчик не может опубликовать свою карточку сам
- Есть тест: подрядчик не видит и не правит чужие карточки, даже подставив
  идентификатор в адрес
- Цена хранится в копейках `bigint`, ни одного `number` для суммы
