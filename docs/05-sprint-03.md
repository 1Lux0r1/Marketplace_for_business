# Спринт 03 — месяц 3, бюджет 62 часа

**Цель месяца:** у площадки появляется собственный пульт управления. Владелец
видит, что происходит, и может менять правила, не трогая код и не дёргая разработчика.

Плюс второй путь клиента: заявка для нестандартных задач.

---

## Администратор — это не оператор

Разница не в правах, а в задачах, и путать их нельзя: это два разных интерфейса.

| | Оператор | Администратор |
|---|---|---|
| Чем занят | сделками: очередь, споры, модерация карточек | самой площадкой |
| Как часто | каждый день, это его работа | несколько раз в неделю |
| Что меняет | состояние конкретной сделки | правила, по которым работают все сделки |
| Кто это | сотрудник поддержки | владелец площадки |

Оператору незачем видеть ставку комиссии, администратору незачем разбирать
очередь заявок. Один интерфейс на двоих даст экран, на котором обоим неудобно.

### Как admin не нарушает границы модулей

§4 `CLAUDE.md` говорит: `admin` читает данные любых модулей, но никогда не пишет.
Это не противоречит тому, что администратор меняет ставку комиссии:

- **Читает** — широко, через представления базы. Свести на один экран данные
  из шести схем иначе нельзя, и это осознанное исключение.
- **Пишет** — только вызовом команды модуля-владельца из его `index.ts`,
  как любой другой сосед. Изменение ставки комиссии делает `payments`,
  блокировку компании — `platform`. Модуль `admin` своих таблиц почти не имеет.

Единственная таблица самого `admin` — журнал действий: кто, что и когда изменил.

## 03-1. admin: каркас, права и журнал действий

Самая важная задача спринта: на журнале будет держаться доверие к площадке.

**Сделать:**

- Схема `admin`, таблица `admin.audit_log`: кто, что, когда, старое и новое значение
- Отдельный раздел приложения с проверкой роли `admin` на каждом запросе,
  а не только в меню
- Запись в журнал делается в той же транзакции, что и само изменение —
  иначе журнал будет врать при откате
- Представления для чтения данных соседних модулей
- Публичный интерфейс: `logChange`, `listChanges`, `getChange`

**Готово, когда:**

- Есть тест: пользователь с ролью `operator` не открывает ни один экран администратора
- Есть тест: откат транзакции не оставляет записи в журнале
- В журнале видно старое и новое значение, а не только факт изменения
- Журнал нельзя отредактировать или удалить из интерфейса — только читать

## 03-2. admin: люди, доступ и компании

**Сделать:**

- Сотрудники площадки: список, выдача и отзыв доступа, смена роли
- Все компании площадки: поиск по названию и ИНН, карточка, история
- Блокировка компании с обязательной причиной, разблокировка
- Кто когда входил в систему

**Готово, когда:**

- Администратор отзывает доступ сотруднику, и активные сессии этого сотрудника
  перестают работать сразу, а не через тридцать дней
- Блокировка подрядчика убирает его карточки из витрины, но не трогает
  его текущие сделки — их доводит оператор
- Каждое действие видно в журнале из 03-1

---

## 03-3. admin: справочники площадки

**Сделать:**

- Категории и зоны: добавление, переименование, скрытие
- Сроки: сбор откликов по заявке, срок заявления рекламации
- Тексты писем клиентам и подрядчикам

**Готово, когда:**

- Есть тест: удалить категорию, по которой есть карточки, нельзя — только скрыть
- Изменение любого справочника попадает в журнал с обоими значениями

**Ставок комиссии здесь нет, и это осознанно.** Решением от 27.08.2026 ставка
перестала быть настройкой и стала подсистемой правил на ~48 часов
(`docs/10-commission-rates.md`). Она делается вместе с модулем `payments`:
управлять ставками, пока по ним не проходят деньги, нечем — проверить
правильность правил можно только на настоящей сделке. Админские экраны
для ставок появятся в том же спринте, что и движок.

## 03-4. admin: деньги и здоровье системы

**Сделать:**

- Сколько сейчас удержано площадкой и по каким сделкам
- Реестр выплат: что готово к выплате, что зависло и почему
- Здоровье: сколько событий не обработано, возраст самого старого,
  ошибки доставки писем

**Готово, когда:**

- Сумма удержанного на экране сходится с суммой по сделкам в статусах
  `paid` и `disputed`, и это покрыто тестом
- Видно событие, которое не обработалось после десяти попыток,
  и текст ошибки по нему

## 03-5. intake: приём заявки

Второй путь клиента (§1): нестандартная задача, для которой нет готовой карточки.

**Сделать:**

- Таблицы `intake.requests`, `request_events` по `docs/03-data-model.md`
- Форма заявки: категория, объект из кабинета клиента, срочность,
  свободный текст, контакт. Зона берётся из объекта, руками не вводится
- Сохранение заявки → публикация `request.created` в outbox в одной транзакции
- Экран оператора: очередь заявок, карточка заявки
- Публичный интерфейс: `createRequest`, `getRequest`, `listRequests`

**Готово, когда:**

- Клиент отправляет заявку и видит подтверждение с её номером
- Есть тест: при ошибке сохранения заявки события в outbox не остаётся
- `parse_source` заполняется значением `operator`; поля под ИИ уже есть, но пустые

## Что этот спринт откладывает

Админский интерфейс забирает почти весь месяц. Подбор с откликами подрядчиков
уезжает на спринт 04, сделка с документами — на 05, деньги — на 06.

Срезать здесь можно только 03-4 (деньги и здоровье системы), перенеся его
в спринт, где появятся сами деньги. Журнал и права срезать нельзя: они и есть
смысл админки.
