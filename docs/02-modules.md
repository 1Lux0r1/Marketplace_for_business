# Модули: ответственность и контракты

## Сводка

| Модуль | Отвечает за | Владеет схемой | Зависит от |
|---|---|---|---|
| `platform` | Организации, пользователи, точки клиента, вход, сессии, роли, outbox | `platform` | — |
| `catalog` | Категории, подрядчики, зоны, карточки услуг, саморегистрация и модерация | `catalog` | platform |
| `intake` | Приём заявки: форма; дальше Telegram и нормализация | `intake` | platform, catalog |
| `matching` | Кандидаты, рассылка предложений, отклики, рекомендации по каталогу | `matching` | catalog, ai |
| `deal` | Сделка: статусы, цена, сроки, переписка, приёмка | `deal` | platform, catalog |
| `documents` | Договор, счёт, акт: шаблоны, нумерация, два пути подписания | `documents` | platform |
| `payments` | Вебхуки, три схемы удержания, движок ставок, выплаты | `payments` | deal |
| `notifications` | Почта, Telegram, шаблоны, ретраи | `notifications` | слушает события |
| `analytics` | Журнал событий, метрики, когорты | `analytics` | слушает события |
| `admin` | Пульт площадки: журнал изменений; дальше люди, правила, деньги | `admin` | ничего не импортирует — см. ниже |

**`admin` не импортирует ни один модуль, и это условие его существования.**
В журнал пишут почти все: `catalog`, когда оператор меняет подрядчика,
`platform`, когда блокируют компанию. Импортируй `admin` их в ответ — вышло бы
кольцо, и выносить его потом пришлось бы вместе с половиной системы. Поэтому
чужие команды он не вызывает: администратор блокирует компанию — это делает
`platform`, вызванный из слоя команд формы, а не из модуля `admin`.

**Список зон живёт в `shared/zones.ts`, а не в модуле.** Это общий словарь:
коды нужны и каталогу (где работает подрядчик), и точке клиента в `platform`.
Владелец-модуль здесь означал бы кольцо в зависимостях, а словарь без состояния
и без логики владельца не требует. Наружу зоны по-прежнему отдаёт `catalog`.

Интерфейсы (`client-web`, `contractor-web`, `admin-web`), демо-режим и тесты
собственных схем не имеют.

Оценки в часах здесь не ведутся — решение от 05.09.2026, см. `CLAUDE.md` §10.8.

## Форма контракта модуля

Каждый `index.ts` экспортирует три вещи и ничего больше:

```ts
// 1. Команды — меняют состояние, возвращают минимум
export async function acceptOffer(input: {
  dealId: string
  offerId: string
  actorId: string
}): Promise<{ dealId: string }>

// 2. Запросы — только читают, возвращают готовый к показу объект
export async function getDealSummary(dealId: string): Promise<DealSummary>

// 3. Типы событий, которые модуль публикует
export type DealAccepted = {
  type: 'deal.accepted'
  dealId: string
  contractorId: string      // идентификатор, НЕ ссылка на catalog
  priceKopecks: bigint
  scheduledAt: string       // ISO 8601, UTC
}
```

Правила формы:

- Команда принимает один объект, а не позиционные аргументы.
- В каждой команде есть `actorId` — кто её выполняет. Проверка прав внутри команды.
- Запрос возвращает данные, готовые к отображению; собирать их в компоненте нельзя.
- В событии — идентификаторы и значения, никогда объекты чужих модулей.

## События системы

| Событие | Публикует | Слушают |
|---|---|---|
| `contractor.registered` | catalog | notifications, analytics |
| `contractor.verified` | catalog | notifications, analytics |
| `contractor.rejected` | catalog | notifications, analytics |
| `listing.submitted` | catalog | notifications, analytics |
| `listing.published` | catalog | notifications, analytics |
| `listing.rejected` | catalog | notifications, analytics |
| `request.created` | intake | matching, analytics |
| `request.parsed` | intake | analytics |
| `offers.collected` | matching | deal, notifications, analytics |
| `deal.quoted` | deal | notifications, analytics |
| `deal.accepted` | deal | documents, notifications, analytics |
| `act.issued` | documents | payments, notifications, analytics |
| `payment.held` | payments | deal, notifications, analytics |
| `payout.released` | payments | notifications, analytics |
| `deal.completed` | deal | payments, notifications, analytics |
| `deal.disputed` | deal | notifications, analytics |
| `deal.cancelled` | deal | notifications, analytics |

`payment.held` вместо `payment.captured`: деньги пришли площадке и **лежат**,
а не зачтены подрядчику. Имя события — это то, что читает разработчик через полгода,
и оно не должно врать про момент, когда деньги становятся чужими.
`payout.released` публикуется только после `deal.completed`, никогда раньше.

`deal.accepted` публикуется одинаково на обоих путях — из каталога и из заявки.
Подписчикам (`documents`, `notifications`, `payments`) не должно быть видно,
откуда пришла сделка: это единственный способ не удвоить весь контур сопровождения.

## Статусы сделки

**У сделки два входа, а дальше один общий путь.** Общий путь — это и есть то,
за что берётся комиссия, и он не должен зависеть от того, как сделка возникла.

```
из каталога:  listing ──▶ new ─────────────────────┐
                                                   │
из заявки:    request ──▶ new ──▶ matching ──▶ quoted ──▶ accepted
                                                              │
                                       paid ◀─────────────────┘
                                         │
                                         ▼
                              in_progress ──▶ act_issued ──▶ act_signed
                                                                  │
                                                                  ▼
                                                              completed
```

**Порядок исправлен 15.09.2026 (задача 04-1).** Раньше здесь было
`in_progress → paid`: подрядчик работает, потом клиент платит. При таком
порядке удерживать в случае спора нечего — клиент просто не заплатит,
и площадка окажется не гарантом, а свидетелем. Это допущение, а не решение:
см. Q22 в `docs/06-open-questions.md`, ответ за разработчиком.

`act_issued` и `act_signed` — из `docs/11-electronic-signature.md`: приёмка
это не кнопка «принять», а подписанный УКЭП акт.

Отмена и рекламация — из тех же точек, что и раньше:

```
new · matching · quoted · accepted · paid · in_progress ──▶ cancelled
paid · in_progress · act_issued · act_signed ──▶ disputed ──▶ completed | cancelled
```

Отменить после подписанного акта нельзя: работа принята, отменять нечего.
Заявить спор раньше `paid` тоже нельзя: деньги ещё не у площадки,
и оспаривать пока не из чего.

| Статус | Означает | Кто переводит дальше |
|---|---|---|
| `new` | Сделка создана. Из каталога — с ценой из карточки; из заявки — цены ещё нет | клиент (каталог) или matching (заявка) |
| `matching` | Только путь заявки: предложения разосланы, идёт сбор откликов | подрядчики или таймер 2 ч |
| `quoted` | Только путь заявки: клиенту показаны варианты с ценой и сроком | клиент |
| `accepted` | Подрядчик, цена и срок зафиксированы | documents, автоматически |
| `paid` | Оплата подтверждена вебхуком, деньги у площадки | payments, автоматически |
| `in_progress` | Подрядчик работает, деньги ждут приёмки | подрядчик |
| `act_issued` | Акт выставлен, клиент его ещё не подписал | клиент |
| `act_signed` | Акт подписан УКЭП — и только отсюда открыт путь к выплате | — |
| `completed` | Работа принята, комиссия начислена, выплата в реестре | — |
| `disputed` | Клиент заявил рекламацию, ручной разбор | оператор |
| `cancelled` | Отменена до начала работ | — |

Переходы, которых нет в схеме выше, запрещены и должны падать с понятной ошибкой.
Это первое, что покрывается тестами — **и тест обязан покрыть оба входа**.
Отдельно проверяется, что `new → accepted` разрешён только для сделки из каталога,
а `new → matching` — только для сделки из заявки: перепутать их значит дать
клиенту зафиксировать цену, которой никто не называл.

Из этого следует требование к модели `deal`: ссылка на заявку **необязательна**
(сделка из каталога заявки не имеет), а ссылка на карточку каталога и происхождение
сделки хранятся явным полем, а не выводятся из того, какие поля заполнены.

## Запасные пути ai-service

| Метод | Что делает | Если недоступен |
|---|---|---|
| `POST /parse` | Свободный текст → категория, срочность, объём, требования | Форма с ручным выбором категории |
| `POST /score` | Заявка + кандидаты → упорядоченный список | Сортировка по правилам: зона, категория, свободен |
| `POST /risk` | Подрядчик + задача → риск срыва 0..1 | Риск нулевой, сделка идёт |
| `POST /price` | Категория + объём + зона → вилка цены | Вилка не показывается |

пойдёт в отчёт по гранту и в питч.
